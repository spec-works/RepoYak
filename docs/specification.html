Abstract

RepoYak turns existing local knowledge workspaces into independently addressable agents. A workspace supplies knowledge, instructions, skills, configuration, and descriptive identity. A local host supplies lifecycle management, AI Catalog discovery, A2A communication, and a shared Copilot SDK runtime with separate persistent conversations for its agents. Git support is optional.

This document captures the requirements embodied in the implementation, including named catalogs, optional custom-agent personas, tracked work, streaming updates, same-task user-input continuation, and local MCP OAuth. It distinguishes host-enforced behavior from instructions given to a model and documents the boundaries of persistence and caller trust.

Status of this document

This is an implementation-derived Editor's Draft, not a W3C publication or a claim of full conformance to every referenced protocol. It describes the local source tree as of 15 November 2026, including optional Git, SDK user input, and local MCP authentication. It is not limited to the contents of an earlier public package.

Requirements use stable fragment identifiers so changes and tests can refer to individual obligations. Examples, notes, implementation links, and appendices are informative. Source links are repository-relative and refer to the implementation accompanying this document.

Scope boundary: date-bound sessions, automatic daily rotation, historical session search, and durable task analytics are proposals, not implemented requirements in this draft. See Appendix B.

This is a self-contained, ReSpec-style HTML snapshot: it uses the abstract, status, conformance, numbered sections, definitions, and references conventions without requiring the ReSpec processor or external assets. The content and navigation remain readable without JavaScript.

1. Scope and conformance

The capitalized terms MUST, MUST NOT, SHOULD, and MAY express mandatory behavior, prohibitions, recommendations, and permitted behavior respectively. Lowercase uses are ordinary prose.

The conformance target is the RepoYak host, including its CLI, registration store, protocol adapters, and Copilot integration. Requirements explicitly addressed to a caller or to agent instructions apply to that actor instead. A model instruction is not an operating-system enforcement mechanism.

  • SCOPE-01 The host MUST expose workspace agents through the implemented A2A bindings and AI Catalog discovery surfaces. It MUST NOT redefine the underlying message, task, artifact, or catalog specifications as RepoYak-specific protocols.
  • SCOPE-02 Registration identity, public descriptive identity, persona selection, A2A task/context identity, and Copilot session identity MUST remain distinct concepts. Selecting a catalog or supplying a context ID MUST NOT select another receiving Copilot session.

Basis: AgentCards, AgentRegistry, and CopilotAgentService. Protocol references are listed in Appendix C.

2. Terminology

Workspace
An existing local folder that supplies an agent's knowledge and supported configuration. It need not be a Git repository.
Agent
A registered workspace binding with a friendly ID, public card, independent task store, and one receiving Copilot session loaded on demand.
Catalog
A named discovery membership list referencing host-wide agents. Membership is not access control.
Persona
An optional SDK-native custom-agent name selected for an agent's session. It is not the agent's public identity or caller identity.
Task
A tracked A2A unit of work with state, history, and result artifacts. Task completion denotes execution completion, not caller acceptance.
Context ID
An A2A correlation handle. It does not partition an agent's history or permissions.
Session
The SDK-managed conversation attached to one agent. Multiple tasks share this conversation; a persisted identifier supports resumption after host restart.
Shared runtime
The host-owned Copilot client/runtime used by all agents, as distinct from their separate sessions.
Pending input
An outstanding SDK user-input or elicitation callback tied to an agent, A2A task, and generated input-request identifier.

3. Host and management

  • HOST-01 repoyak start MUST restore saved registrations, or create an empty registry if none exists. An optional initial workspace MUST seed only a new registry; it MUST NOT resurrect a removed registration on later starts.
  • HOST-02 Startup MUST run in the foreground by default. serve and the single-workspace invocation MUST remain foreground aliases. start --background MUST be Windows-only and append background output to host.log in the selected state directory.
  • HOST-03 add, list, remove, and stop MUST manage an already running host through a same-OS-user named pipe. The host MUST NOT expose these administration operations as an HTTP management API.
  • HOST-04 stop and normal host shutdown MUST stop hosted agents and release their runtime resources without deleting workspace files, saved registrations, or saved session references.
  • HOST-05 Removing an agent globally MUST cancel and join its outstanding work, dispose its session/server, and remove its registration and catalog memberships. Other registered agents MUST remain available. Saved session state and workspace files MUST NOT be deleted by removal.
  • HOST-06 list MUST report registration ID, workspace path, status, error, card URL, persona, and catalog memberships. Failed registrations MUST remain visible to management and MUST NOT appear as available catalog entries.

Implementation: HostCommands, AgentAdmin, AgentRegistry.

4. Workspace registration

  • REG-01 Registration MUST accept an existing local folder without requiring Git metadata. The CLI MUST resolve a supplied workspace path to an absolute path before sending it to the registry; the registry MUST reject non-absolute workspace paths.
  • REG-02 Explicit agent IDs MUST contain 1–64 lowercase ASCII letters/digits, separated only by single hyphens. When no ID is supplied, the host MUST derive one from the workspace folder name, not from mutable README text.
  • REG-03 Duplicate agent IDs and normalized workspace paths MUST be rejected, except for the explicit catalog-membership operation in CAT-02. The host MUST NOT silently rename a duplicate.
  • REG-04 When allowed roots are configured, registration MUST restrict paths to those roots or their descendants using directory boundaries. Workspace paths traversing symbolic-link or junction ancestors MUST be rejected. Without allowed roots, the same-user management client MAY register any otherwise supported local folder.
  • REG-05 A registered workspace MUST have exclusive running ownership, including across hosts. A second runtime registration attempting to own the same canonical workspace MUST NOT load a competing session.
  • REG-06 A .git file or directory at the workspace root MUST enable Git support. The host MUST re-evaluate that condition for each work request, including metadata added or removed after registration.

Implementation: ID and registration types, workspace validation, Git detection, workspace ownership locks.

5. Configuration and persistence

  • CFG-01 All host/management commands MUST accept --config and --port. Port selection MUST use explicit option, configured file port, REPOSITORY_AGENT_PORT, then 5080, in that order. Invalid ports outside 1–65535 MUST be rejected.
  • CFG-02 The persisted configuration MUST contain durable host identity, agent registrations, and catalog memberships; the CLI-selected port MUST be saved at startup. Legacy files without catalog memberships MUST migrate to default without changing host/agent identities.
  • CFG-03 Configuration ownership MUST be exclusive, and registry updates MUST write a temporary file before replacing the saved configuration. Changes made manually MUST be loaded on restart rather than treated as live configuration updates.
  • CFG-04 Explicit configuration MUST use <config-path>.state for runtime state. Without it, the host MUST honor REPOAGENT_STATE_DIRECTORY, or use the OS local-application-data directory under AgentDock\hosts\port-<port>. Management pipe identity MUST distinguish the user, port, and selected configuration.
  • CFG-05 Background startup MUST preserve the selected configuration and port in the child host. Selecting another configuration MUST NOT implicitly migrate saved session files.
  • CFG-06 Tasks MUST persist by default. Startup --no-persistent-tasks MUST override and save persistentTasks: false; in-memory mode MUST NOT modify an existing ledger. Startup settings MUST be forwarded to background children. Old configurations MUST default to persistence enabled and single sessions.
  • CFG-07 Startup --default-session-mode and registration --session-mode MUST accept only single or daily. Agent overrides MUST be persisted. Daily MUST be reported as reserved with a warning; effective behavior MUST remain single until synthesis and recall ship. Management views MUST distinguish requested and effective modes.

Operator guidance: use the same configuration and port for startup and management. Independent host processes still require different listening ports. Stop the host before editing its configuration file manually.

Implementation: HostConfiguration, startup configuration, registry persistence, pipe identity.

6. Catalogs and agent discovery

6.1 Catalog membership

  • CAT-01 The host MUST maintain a default catalog. A new registration without --catalog MUST join it. Catalog names MUST use the agent-ID syntax.
  • CAT-02 An explicit add --catalog for the same ID/workspace and a compatible persona MUST add membership idempotently without replacing the runtime or conversation. It MUST NOT change that agent's workspace or persona.
  • CAT-03 remove <id> --catalog <name> MUST remove only membership, leaving the agent callable even if it has no memberships. Empty catalogs MUST remain available. list --catalog MUST filter by membership.
  • CAT-04 Catalog responses MUST be generated from ready live registrations and include card URLs with media type application/a2a-agent-card+json. An agent's identifier MUST use urn:air:{hostId}.localhost:{agentId}, without a kind suffix, and remain the same across catalogs and host restarts. The publisher segment MUST derive from the persisted host ID, not the serving address or port.
  • CAT-05 Catalog documents MUST declare specVersion: "0.9" and use the Spec-Works AI Catalog library's models, Discoverable-level structural validation, and JSON serialization. Invalid generated documents MUST NOT be served. Optional null fields MUST be omitted. Structural validation MUST NOT be presented as signature or trust verification.

  • DISC-02 Cards MUST advertise HTTP+JSON first, JSON-RPC compatibility, protocol version 1.0, streaming support, and text/plain and application/json input/output modes. These modes MUST NOT be interpreted as a promise of arbitrary binary-input processing.

Implementation: catalog membership and entries, routes, cards, descriptive identity.

The integration uses SpecWorks.AiCatalog 0.7.0. The prior custom generator labeled documents 1.0; this integration corrects that label to the library's supported 0.9 model. Routes and memberships remain unchanged. RepoYak retains its own ASP.NET endpoints; the library supplies catalog processing, not hosting.

Agent entries now replace urn:agentdock:{hostId}:agent:{agentId} with local, host-scoped AIR identifiers. Consumers need to refresh cached catalogs and stored entry references. The host's urn:agentdock:host:{hostId} identifier, registration IDs, and saved runtime sessions are unchanged. Identifier syntax does not establish publisher ownership or trust.

7. Messages, tasks, and streaming

  • TASK-01 A new nonempty text work request MUST create a tracked A2A task. Empty requests and the explicit /new-session control MUST return Messages rather than work Tasks.
  • TASK-02 Task stores MUST be isolated per agent. Retrieval, subscription, cancellation, and input replies MUST target the same agent that owns the task. Revisions after terminal completion MUST be new work, not resumed terminal tasks.
  • TASK-03 Successful work MUST emit Submitted and Working status, a final text artifact named Result, then Completed. Public assistant intent/message updates MUST be forwarded as Working status messages except while input or sign-in is pending.
  • TASK-04 The host MUST NOT forward reasoning events or raw tool arguments/results as progress events. Final artifact output MUST NOT be represented as token-by-token artifact deltas in this implementation.
  • TASK-05 Synchronous sends MUST wait for terminal status or a valid pending-input/sign-in boundary. Explicit return-immediately requests MUST return without waiting for completion. Streaming sends and subscriptions MUST allow observation of task events, stopping at an input-required or auth-required boundary while preserving the original execution.
  • TASK-06 Execution failures MUST produce a Failed task and log the underlying exception. Ordinary execution exception details MUST NOT be included in the public failure message. An unavailable persona MUST instead receive an explicit persona-selection explanation.
  • TASK-07 Cancellation MUST propagate to active execution. Cancelling a waiting synchronous caller MUST attempt to cancel its task. An SDK turn MUST have a ten-minute execution timeout, including time spent waiting for input; timeout MUST abort the turn and fail the task.
  • TASK-08 Persistent mode MUST store sanitized snapshots, caller messages, artifacts, and state transitions transactionally at <host-state>\history.db. Owner scope MUST include durable host ID, agent ID, and canonical workspace, independent of catalogs and AIR identifiers. Restart, rotation, and re-registration of that binding MUST retain history. Duplicate saves MUST NOT duplicate transitions or undo terminal outcomes.
  • TASK-09 Persistent startup MUST reconcile unfinished tasks to Failed with an interruption/outcome-unknown explanation and preserve partial results. It MUST NOT replay work or reconstruct pending callbacks. A failed storage write MUST NOT publish a durable completion; affected observers MUST terminate and new host admissions MUST be blocked until repair/restart.
  • TASK-10 Snapshots and transitions MUST NOT archive known local MCP sign-in links or credential fields. Pending sign-in snapshots MAY retain links only in process memory for live callers. Operators MUST NOT treat filtering as encryption, caller isolation, or reliable redaction of arbitrary pasted secrets.

Ending observation at an input boundary is not cancellation. A task may outlive a detached response or stream. Completed means that execution ended successfully; it does not certify the quality of the result or caller approval.

Implementation: RepositoryAgentHandler, InputAwareA2AServer, durable task store, SDK execution and timeout.

8. User input and elicitation

8.1 Request contract

  • INPUT-01 Both SDK user-input and elicitation callbacks MUST transition the original A2A task to InputRequired (rendered as input_required by clients). The SDK turn MUST remain alive awaiting the reply; the host MUST NOT start another SDK turn to answer that callback.
  • INPUT-02 The status message MUST include question text and a JSON data part with the fields below. The host MUST generate a new request ID for each pending question.
Input-required data part
FieldMeaning
requestIdIdentifier for this pending question; not the A2A task ID.
kinduser_input or elicitation.
questionHuman-readable prompt.
choicesOffered answers, or null when absent.
allowFreeformWhether an answer outside the choices is permitted for user input.
requestedSchemaForm schema supplied by the SDK, or null.
urlURL elicitation target, or null.

8.2 Reply and continuation contract

  • INPUT-03 A reply MUST address the same agent and task. A valid reply MUST resolve that task's pending callback and return it to Working; repeated questions MUST be supported in the same original turn.
  • INPUT-04 The host MUST reject replies when no input is pending, when the request has already been answered, or when a supplied requestId does not match. Invalid replies MUST NOT consume the pending question. Structured clients SHOULD include requestId; plain interactive replies MAY omit it.
  • INPUT-05 User-input replies MUST accept nonempty text or an object containing answer. When freeform input is disabled, answers MUST exactly match an offered choice.
  • INPUT-06 Elicitation replies MUST accept actions accept, decline, and cancel, supplied through structured data or JSON text. Plain decline and cancel MUST also be accepted. Accepted non-URL forms MUST contain a content object with the schema's required top-level fields. The host MUST NOT claim complete JSON Schema validation.
  • INPUT-07 URL elicitation MUST surface the URL without opening it. Plain accept, decline, or cancel MUST be supported for URL acknowledgements. An elicitation action MUST NOT be treated as an A2A task-cancellation request.
  • INPUT-08 Pending questions within a turn MUST be serialized. Late progress messages MUST NOT replace InputRequired with Working while the question is unanswered. Continuation observation MUST suppress already-answered input snapshots rather than stop on the stale question.
  • INPUT-09 Cancellation/shutdown MUST release pending callback waits. /new-session MUST be rejected while input is pending. The input bridge MUST NOT fabricate a trusted-human identity or change automatic tool-permission approval.

Privacy: input replies become part of task history. Callers should not send credentials or secrets. A URL acknowledgement does not establish authentication, and declining a form does not necessarily terminate the task.

Implementation: input records, pending input and reply validation, input-aware responses, SDK callback mapping.

9. Runtime and session continuity

  • SESSION-01 The host MUST own one shared Copilot runtime, started lazily on first work or explicit session rotation. Concurrent first requests MUST NOT create duplicate shared runtimes. Registration alone MUST NOT start a Copilot process or load a session.
  • SESSION-02 Each agent MUST own one receiving session with serialized turns. Different agents MAY execute concurrently. A request MUST target its agent's session object rather than a process-wide current-session selector.
  • SESSION-03 The active session identifier MUST be persisted under host state, scoped to agent ID and canonical workspace path. Reusing an ID for another workspace MUST NOT reuse the former workspace's session. Supported legacy session references MUST be imported when no current reference exists.
  • SESSION-04 First work after restart MUST resume the saved session when present. Empty/invalid references and resume failures MUST be reported rather than silently replaced with a fresh conversation.
  • SESSION-05 Explicit /new-session MUST create fresh continuity, save its new identifier, and dispose the prior loaded session. Existing A2A task records MUST remain unchanged. Rotation MUST NOT imply deletion of workspace data.
  • SESSION-06 An optional persona MUST be persisted with registration and selected through SDK-native session APIs on create, resume, rotation, and before work. Availability MUST be checked on demand; missing/disabled personas MUST NOT silently fall back to another persona.
  • SESSION-07 Stopping an agent MUST dispose its session without disposing the shared runtime used by peers. Host shutdown MUST dispose the shared runtime. Shared-runtime failure MUST NOT silently trigger replacement conversations or automatic failover.

All callers and A2A contexts for one agent share its conversation. Catalog membership neither creates sessions nor partitions history. Loaded sessions have no idle eviction. A saved SDK session reference is not a durable RepoYak task archive.

Implementation: shared runtime, session lifecycle and persona selection, agent shutdown.

10. Workspace grounding and tools

  • GROUND-01 Each work request MUST scan supported workspace text files for relevant grounding, rather than rely only on a startup snapshot. The scanner MUST skip configured dependency/build/SCM directories and reparse-point files/directories and apply bounded file/context limits.
  • GROUND-02 The runtime MUST use the workspace as its working directory, enable supported instruction/configuration discovery and skills, and supply discovered skill roots. Workspace custom-agent roots MUST be available; explicit persona selection MUST also allow the host user's custom-agent directory.
  • GROUND-03 MCP definitions MUST be discoverable through supported Copilot configuration without host-imposed exclusions by server name. Explicit host settings MUST take precedence; registration MUST NOT bypass runtime folder trust, server authentication, or managed policies.
  • GROUND-04 Repository file hooks and standalone CLI extensions MUST be explicitly disabled, including when experimental mode is enabled. SDK session-store retrieval MUST remain disabled in the current integration.
  • GROUND-05 Host-provided agent instructions MUST treat workspace material as evidence rather than authority to override the request, require workspace-relative citations for factual answers, and distinguish current facts from dated/exploratory material or missing evidence.
  • GROUND-06 For Git-enabled workspaces, host instructions MUST require working-tree/branch/upstream checks and permit git pull --ff-only only with a clean tree and configured upstream. They MUST require update blockers to be reported and forbid forced synchronization, switching branches, changing remotes, merging, rebasing, stashing, or discarding changes to force freshness.
  • GROUND-07 For non-Git workspaces, host instructions MUST require use of current local files without assuming a branch/upstream and forbid Git commands or initialization unless explicitly requested. General work instructions MUST preserve unrelated work and prohibit unrequested destructive changes, commits, pushes, or pull requests.

GROUND-05 through GROUND-07 specify instructions supplied to the model, not mechanical enforcement or guaranteed model compliance. Git refresh is not a registration/startup operation. Workspace configuration discovery can launch MCP processes or contact external services; it is not an offline-only promise.

Implementation: workspace scanning, system prompt and SDK configuration.

11. Security and privacy

  • SEC-01 The HTTP listener MUST bind to IPv4 loopback, not a remote-accessible interface. HTTP A2A MUST NOT be presented as authenticated or restricted to the same OS user merely because the management pipe is same-user.
  • SEC-02 The current integration MUST use the host account's runtime authentication and automatic tool-permission approval. It MUST NOT claim caller-specific credentials, per-caller history isolation, per-tool human approval, or an OS sandbox.
  • SEC-03 Host instructions MUST forbid exposing credentials/private data and accessing files outside the configured workspace. Documentation MUST distinguish these instructions and registration checks from the actual authority of SDK tools running under the host account.
  • SEC-04 Operators MUST use trusted local callers, workspaces, and discovered tool configurations and restrict hosted data to material approved for the configured inference service. Persona selection MUST NOT be described as granting app history, private memory, or unconfigured external-service capabilities.

Trust model: a local process able to reach A2A can request file edits and commands under the host account. Separate sessions and catalogs are not security boundaries. Remote exposure requires additional authentication and approval design outside this specification.

Implementation: loopback listener, same-user pipe, permission handler and instructions, default client authentication configuration.

11.1 Local personal-agent authentication

The implemented deployment profile is a local personal agent operated by the user. It can obtain delegated credentials directly through the user's browser, without an inbound OAuth/OBO chain. A hosted delegated agent would instead require authenticated/authorized callers, user/tenant isolation, delegated token exchange such as OBO, and applicable client registration, consent, and tenant approval. That hosted profile is deferred, not enabled by a deployment switch.

  • AUTH-01 Each session MUST provide authenticate_mcp. Without serverName, it MUST passively list only configured server names, enablement, and observed connection states. With a name, it MUST accept only an exact enabled configured server and MAY start that server by name if needed. Agent instructions MUST direct use when a needed MCP requires sign-in, rather than prompting for every configured MCP before each task.
  • AUTH-02 For a selected server in needs-auth, the host MUST use the runtime-managed authorization-code login with its default loopback callback. The runtime, not an A2A message, MUST receive and exchange the code. The host MUST NOT register a host-managed-token callback for this flow.
  • AUTH-03 A browser sign-in wait MUST emit AuthRequired on the original task, with human-readable instructions and a data part containing only requestId, kind equal to local_mcp_oauth, serverName, and authorizationUrl. Authorization links MUST be absolute HTTPS or loopback HTTP URLs without user-info. They MUST NOT be opened automatically.
  • AUTH-04 The matching session/server connection event MUST confirm completion before the original SDK turn continues. A caller reply or browser callback page MUST NOT be treated as proof of sign-in. Callers MUST poll or resubscribe to the task, not send a work-message continuation to acknowledge authentication.
  • AUTH-05 Input and sign-in prompts MUST be serialized; late progress MUST NOT obscure a pending prompt. /new-session MUST be rejected while either is pending. Cancellation/shutdown/turn timeout MUST release the wait and attempt bounded MCP-server cleanup. A late callback MUST NOT complete a canceled A2A task.
  • AUTH-06 The authentication bridge MUST NOT solicit or forward tokens, authorization codes, callback URLs, raw challenges, or client secrets through A2A or its model-facing results. Authentication-tool exceptions MUST produce a sanitized outcome rather than expose provider responses.
  • AUTH-07 MCP OAuth token storage MUST be explicitly in-memory for the loaded session. Documentation MUST NOT claim persisted MCP tokens, per-caller credential isolation, inbound A2A authentication, or hosted/OBO support from this bridge.

The browser must run on the RepoYak machine, and the selected OAuth client's registration must permit the runtime's loopback redirect. Fixed incompatible callbacks are not bypassed. Arbitrary login flows implemented inside stdio MCP executables are not intercepted. The bundled runtime can leave denied/invalid manual logins in needs-auth without a terminal error; in that case the caller should cancel, otherwise the ten-minute turn timeout ends the wait. Cleanup is best effort, bounded to five seconds.

Implementation: runtime-managed MCP login, authentication request, A2A auth state and continuation, tool and SDK configuration.

12. Distribution and compatibility

  • DIST-01 The .NET tool MUST use manifest package SpecWorks.RepoYak.Cli and command repoyak. Full multi-platform packaging MUST produce matching-version implementations for win-x64, win-arm64, osx-x64, and osx-arm64. Installation MUST select the matching implementation through the manifest.
  • DIST-02 Tool output MUST be self-contained with the required .NET/ASP.NET and matching SDK-bundled Copilot runtime assets. It MUST preserve required hidden plugin markers, license, specification linkset, plugin manifest, and consumer skill. Installing the platform-specific tool MUST require .NET SDK 10 or later; installed execution MUST NOT require a separate .NET runtime installation.
  • DIST-03 Public package publication MUST require explicit workflow dispatch requesting publication, after pack/test and advertised-platform installed-tool verification jobs succeed. RID packages MUST be published before the manifest. Building or installing locally MUST NOT be represented as publication.
  • DIST-04 The consumer plugin MUST provide root plugin.json and skills/repoyak-cli/SKILL.md. Plugin installation MUST NOT itself install executables, authenticate an account, start the host, or grant permission to invoke agents. Executable-package version overrides MUST NOT implicitly rewrite the plugin version.
  • DIST-05 Rebranding MUST preserve compatible legacy state directories, pipe naming, host urn:agentdock:host: identifiers, environment-variable names, and saved session references. Agent entry identifiers follow CAT-04. The current tool MUST NOT imply that it installs a rahcli alias.

Standalone publishing and local single-RID packages are supported development paths, not evidence that every advertised platform has been verified for that build. Installation does not establish an authenticated Copilot subscription. No OS service, launch agent, or auto-start registration is installed.

Implementation: package project, release workflow, installed-tool verifier, plugin packer. See packaging guide, plugin guide, and incubation ADR.

B. Limitations and deferred work

This appendix records current boundaries. It does not impose proposed functionality on the existing implementation.

Task and input durability
A2A task records, pending input/sign-in, and MCP OAuth tokens are in memory. Restart or unregistering loses them even when the SDK conversation can be resumed. Pending callbacks cannot resume across restart.
Historical and date-bound sessions
There is one saved active-session pointer per agent/workspace. No date-indexed session catalog, timezone/day assignment, daily or agent-suggested rotation, historical retrieval tool, or durable task-completion analytics exists. Questions such as "what did we work on yesterday?" are not guaranteed by this contract.
History administration
Task get/list can read durable records. No public history export/deletion UI, automatic retention, encrypted ledger, or SDK transcript migration is implemented. Keep live SQLite state on local disk; schema initialization uses FULL synchronous transactions and a bounded busy timeout. Task persistence is not SDK conversation indexing.
Runtime resilience
No idle-session eviction, runtime pool, automatic failover, or silent recovery into replacement sessions exists. A shared-runtime failure can affect every hosted agent.
Authentication and permissions
Local runtime-managed MCP OAuth is implemented as described in 11.1. Hosted callbacks/OBO, per-caller authentication/credential partitioning, an OS sandbox, and permission-approval bridging are not implemented. Tool permissions remain automatically approved.
Input schema validation
The host checks reply shape, actions, choices, request IDs, and presence of required top-level form fields. It is not a complete JSON Schema validator.
Transport and output
The implementation does not claim every optional A2A feature, remote deployment support, or token-level result streaming. Media-mode advertisement is not arbitrary multimodal support.
Workspace providers
Local folders are supported, with optional Git behavior. URL cloning and provider-specific support for other source-control systems are not implemented.
Platform installation
macOS background hosting, service/launch-agent installation, macOS privacy permission grants, and signing/notarization of a standalone public binary distribution are not provided by the current mechanism.
