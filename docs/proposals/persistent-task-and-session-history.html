Proposal for review — not implemented

Persistent Task and Session History

RepoYak · Updated 27 November 2026 · Local personal-agent profile

Recommendation: introduce a durable local history ledger for A2A tasks and an explicit registry of physical SDK conversations. Treat today's conversation as working context and pair daily rotation with end-of-day synthesis of source-linked memories and bounded next-day recall. Ship persistence and retrieval first, then the combined daily compaction cycle. Daily sessions need not align exactly with midnight: rotate between tasks rather than interrupt active execution.

Prepared against the current local implementation and the imported Design Note: Agents, Tasks, and Sessions. This document proposes changes; the implementation specification and host contract remain descriptions of existing behavior.

2. Current implementation and integration seams

  • AgentRegistry now uses SQLite task storage by default at <host-state>\history.db. Sanitized snapshots/transitions and caller messages survive restart and re-registration of the same owner binding. --no-persistent-tasks saves an in-memory opt-out without touching an existing ledger. This is the first delivery, not the session/memory design below.
  • CopilotAgentService serializes turns and maintains one loaded SDK session per agent. active-session.txt persists only the current session ID, scoped to friendly ID and canonical workspace; it is not a history index.
  • RepositoryAgentHandler owns the task lifecycle and input/authentication callbacks. InputAwareA2AServer returns at interrupted boundaries while the original producer stays alive. Those callbacks cannot be reconstructed merely by restoring a task snapshot.
  • RepositoryKnowledge searches bounded workspace text. It does not query task/session history. Daily rotation, historical retrieval, and daily summaries are not implemented.

The pinned SDK package declares ListSessionsAsync, GetSessionMetadataAsync, and session GetEventsAsync. Its XML contract says disposal preserves session state on disk. These APIs are integration candidates, not evidence of a complete, stable, privacy-filtered historical export. Validate their behavior against the bundled runtime before relying on them; do not scrape undocumented SDK storage files or index unrelated Copilot sessions.

Task persistence belongs at the task-store boundary; session registration and task/session binding belong where the service selects the actual SDK session. An SDK session ID is not an A2A context ID. Preserve protocol correlation without turning caller context IDs into receiving-session selectors.

3. User outcomes and scope

After restart, callers should retrieve previous task messages and results, inspect which sessions held the work, and ask time-based questions without managing SDK session IDs.

QuestionRequired evidence
What did we work on yesterday?Agent-scoped task/message activity in the resolved date interval, including unfinished work, with summaries and record citations.
How many tasks did we complete Friday?Distinct tasks whose durable terminal state is Completed and whose completion time falls in the specified interval. Report scope and distinguish tasks from accepted outcomes.
Remember that project from last Wednesday?Resolve the date, search that agent's summaries and session/task history, then cite matches or request clarification.
What was the result of task X before restart?The same owner-scoped task ID, persisted state, messages, and artifacts, regardless of the current SDK session.

Non-goals for the first delivery: automatic replay of interrupted work; durable OAuth tokens; all tool/reasoning traces; a distributed saga engine; per-caller security; hosted/OBO deployment; inventing results for tasks lost before persistence existed. Session history must be designed now, but daily rotation need not ship with the first durable store.

4. Domain model: separate ownership, context, and memory

Agent identity
A durable history scope with an opaque key and friendly ID/workspace snapshots. Initially associate it with the host's existing agent-ID/canonical-workspace pairing. Re-registering that pair restores the same scope; reusing the friendly ID for another workspace creates a new one. Workspace moves/renames need explicit migration, not heuristic merging.
Task
A protocol unit of work with exactly one owning agent, immutable task ID, optional context ID, current A2A snapshot, timestamps, and a terminal outcome. It can have activity on several days. Revision/retry after a terminal outcome creates another task with a relationship to its origin.
Session
A physical SDK conversation for one agent, with identity, day assignment, actual start/end, and split reason. A new session means creating a new SDK conversation, not slicing an existing transcript. Tasks and sessions are separate entities.
Task/session association
A task's actual execution interval or segment linked to the selected session. Allow multiple associations instead of assuming every task permanently fits in one day/session. The minimal implementation writes one association when the service acquires its turn gate and selects the SDK session.
Task relationship
A typed link such as delegated-to, transferred-to, retry-of, or refinement-of. Reference both owning agent identity and task ID, plus remote endpoint identity when needed. External task status is an observation, never something this store authoritatively updates.
Daily summary / memory
Derived knowledge owned by the agent, independent of a particular session, with source links, interval, version, and coverage watermark. Synthesize decisions, commitments, unresolved questions, and useful discoveries, rather than only shortening the transcript. These are revisable interpretations, not authoritative facts or authorization to continue an old request.

A router can complete its task with a routing outcome and link to the specialist task. This transfers user-facing accountability, not ownership of the original task object. A delegating entry agent retains its own task and synthesizes the results of related tasks. A conference does not give participants permission to update each other's task state.

A shared context ID can correlate tasks; it neither proves parentage nor uniquely identifies a saga. Store explicit relationships. Initial persistence may reserve that model without introducing new public protocol fields or implementing routing.

5. Recommended persistent ledger

Use one local SQLite database at <host-state>\history.db, logically partitioned by durable agent identity. The combined name anticipates both task and session records. The first delivery adopts SQLite for tasks, retained owner scopes, transactional transitions, known-auth filtering, and crash reconciliation; session tables below are still proposed. SQLite's application-file documentation supports structured local state with transactional updates.

A host-wide database is simpler for atomic task/session binding and cross-agent relationship queries. It differs from the note's per-agent-folder vision: the workspace stays the agent's knowledge boundary, while private execution history stays outside its repository. Agent-specific export can later provide portable archives without writing live ledgers into Git or synced knowledge folders.

5.1 Write and observation contract

Implement the pinned A2A ITaskStore contract first, verifying every method and serialization field against the installed package. Preserve messages, artifacts, metadata, paging, filters, and terminal-state rules. Write a snapshot plus any state transition in a single database transaction. Persist acknowledgements before exposing them to callers; verify the A2A notifier's actual ordering instead of assuming the interface alone guarantees this.

Use revision/sequence checks so duplicate persistence calls do not append duplicate transitions or undo terminal states. Messages and artifact changes can update the snapshot without generating an artificial state transition. No full event-sourcing framework or promise of replaying every historical SSE frame is needed.

Choose local-disk transactions, a bounded busy timeout, explicit schema migrations, and a durability setting tested for the intended crash guarantee. Consider WAL for overlapping readers/writers, but keep its live files on local disk and use SQLite's backup API for consistent backups; see WAL documentation and Online Backup API. Do not copy a live main database alone or place its WAL files in OneDrive/network storage.

A failed write must not be reported as a successful durable completion. Stop admitting new work when the ledger is unavailable, surface an explicit storage failure, and log the condition. There is no atomic transaction across SQLite and an external command: a crash after a side effect but before its completion record leaves an unknown outcome. This limitation rules out blind replay.

5.2 Relationship to SDK storage

SQLite is authoritative for RepoYak task state, session associations, and its sanitized history archive. SDK persistence remains responsible for runtime conversation resumption. A missing SDK transcript must not erase task results. Conversely, an SDK transcript is not proof that a task reached durable Completed.

For historical sessions, use only recorded RepoYak-owned SDK IDs. Evaluate GetEventsAsync on disposable sessions after resume and after disposal/restart. Extract an allowlisted user/assistant projection into the ledger with stable source identities; do not import raw OAuth/tool events. Treat historical backfill as optional and coverage-labeled, not a prerequisite for returning task snapshots.

6. Session registry, days, and rotation

6.1 Addressing and user-local time

Rollout control: persisted defaultSessionMode accepts single or daily, selected by startup --default-session-mode. An agent can override it through registration --session-mode or its saved sessionMode. The initial default is single. Daily settings are validated and retained but do not enable rotation before synthesis/recall exists; management reports effective single mode and startup warns about the reserved policy.

The conceptual day address is (agent-history-key, day-policy, local-date). It resolves to an ordered collection of sessions; an empty day is valid. A specific session adds an immutable session ID and ordinal. URLs and SDK IDs need not encode that structure, and no new client syntax is required to ask about Wednesday.

For the current local profile, use one explicitly configured operator timezone/cutoff policy inherited by agents. Do not infer a different user identity or timezone from unauthenticated callers. Initialize the policy from the local operator's timezone and a midnight cutoff as a proposed default; a 4 a.m. workday cutoff is configurable, not silently imposed by this note.

Construct each interval from local civil-time boundaries and convert those instants to UTC. Do not assume days last 24 hours or subtract four elapsed hours across daylight-saving transitions. Define deterministic handling for nonexistent/ambiguous cutoff times (advance through a gap; choose the earlier occurrence during a fold) and test the supported Windows/macOS timezone mapping.

Persist UTC event times plus the timezone/cutoff/policy revision used for session day assignment. Policy changes affect future assignments, not old labels. Query responses show absolute interval, timezone, and calendar-day or workday mode. Ordinary "Friday" means the calendar date unless the caller requests the configured workday; clarify ambiguous relative dates rather than silently choose a surprising interval.

6.2 Physical daily conversations with flexible boundaries

Decision recorded, 22 November 2026: daily sessions are physical SDK conversations. They do not have to map exactly to midnight-to-midnight intervals. Use option A below; logical history slices are not sessions, and the clock does not force interruption of an active turn.
Design rationale recorded, 27 November 2026: the day is a human-aligned working-context boundary. During today's conversation, the user expects the agent to retain the context of earlier exchanges today without explicitly recalling each one. At day's end, review that working context and synthesize durable memories; the next day's fresh conversation retrieves relevant memories rather than inheriting the full transcript. This is the intended compaction cycle, not a claim about human cognition or a guarantee of unlimited SDK context.
OptionBehavior and cost
A. Rotate physical sessions between tasks — selectedLazy daily rotation before the next new task after the assigned day changes. Finish a pending turn in its existing SDK session and attribute messages to their real dates. A session can span the boundary; its assigned day is a navigation label, not a claim that all its activity occurred on that day.
B. Day-contained logical history slices — not selectedSplit recorded history without creating a new SDK conversation. Date-based projections may still be useful for queries, but they are not session identities or session rotation.
C. Force physical cutoffCancel/checkpoint the active turn and start a new SDK session. Current callbacks and side effects are not safely checkpointable, so this risks lost work, unnecessary failure, and duplicate execution. Not recommended without a separate durable execution design.

Proposed execution policy: assign a new physical session to the configured local day when its first task begins. Before each subsequent new task, after acquiring the agent's turn gate, compare that day's assignment with the current day. If it differs, create a fresh SDK conversation before executing the task. Continuations of pending input/authentication remain in the existing turn and session, even across the boundary. An idle session need not be closed by a midnight timer; rotate lazily when new work arrives. This is a day-based policy, not a maximum elapsed lifetime of 24 hours.

Find Wednesday's work by actual task/message activity during Wednesday's resolved interval, including a conversation assigned to Tuesday that continued into Wednesday. Return the physical sessions containing those matches. The assigned day groups newly started conversations; it must not exclude activity on adjacent dates. Session history records both assignment and actual activity range.

A task accepted before the cutoff but queued behind another turn binds to the session actually selected when execution begins. Creation date, activity date, and completion date remain independent. An idle agent creates no empty daily session; "at least one per day" means each day on which work executes.

Keep same-day turns in the existing conversation by default. A day may still contain several physical sessions after an explicit split or a recoverable lifecycle event; daily synthesis reviews all recorded activity in that day's interval, not just one session. The SDK can still compact its own context within a conversation. Daily rotation is a deliberate longer-lived context boundary, not a substitute for runtime context management.

6.3 Further splits and continuity

Allow explicit user rotation and future agent-requested splits for idle gaps, topic shifts, or context pressure. Accept splits only between turns, with a recorded reason and previous/next linkage. No hard idle threshold or token limit is adopted here. Defer the agent-requested rotation tool until the registry and retrieval mechanism exist.

A fresh session is a real context cut: no automatic transcript copying or hidden replay. Normal workspace grounding, persona, and tool configuration still apply. Pair daily rotation with a bounded, host-controlled memories-first recall policy: at the first new turn, provide relevant prior-day memories as attributed historical context, with coverage indicators and source references. The new request determines relevance; neither the prior transcript nor every accumulated memory is copied wholesale. Exact selection, context budgets, and operator controls remain implementation decisions.

Daily rotation and synthesis/recall form one designed feature. Persistence may ship first, but automatic daily rotation should not ship alone and make yesterday's useful context inaccessible. Read-only model tools should support bounded agent-scoped history search and retrieval of referenced task/session records; tool names and schemas remain to be defined. They read sanitized history without resuming historical SDK conversations, exposing arbitrary SQL, or authorizing unfinished work.

Session rotation must record the prepared session, validate persona/configuration, then atomically switch the ledger's active reference before admitting another turn. Creation and database commit cannot be atomic with the SDK: record recoverable preparation/orphan states, keep the previous reference until commit succeeds, and never silently replace a failed resume with a new conversation.

Local MCP tokens are currently in-memory per loaded SDK session. More frequent physical rotation can require more sign-ins. Do not change token persistence, introduce OBO, or pretend logical history slices have independently authenticated runtimes as a side effect of this feature.

7. Restart, migration, and lifecycle

Persisted history survives restart, unregistering, and rotation. Removing catalog membership changes navigation only. Unregistering stops the agent but retains its history; explicit history deletion is a distinct authorized operation. A future archive/revive feature can reuse that separation.

At startup, reconcile tasks left Submitted, Working, InputRequired, or AuthRequired by the previous process. Without durable execution resumption, transition them to Failed with a public interruption explanation and an internal outcome-unknown reason. Preserve prior states/messages and any partial artifacts; do not reopen a terminal task or replay commands. Canceled tasks remain canceled even if a late callback or stale writer arrives.

On graceful shutdown, apply the existing cancellation semantics and commit final states before closing the store. After a crash, failure denotes that RepoYak cannot establish completion, not proof that every external action failed. A fresh retry must be explicit and can link to the interrupted task.

Import the existing active-session.txt as a legacy session record with unknown day and coverage where metadata cannot establish them. Do not assign a multi-day legacy conversation to today's day or manufacture old tasks from transcript text. Keep the pointer readable during migration, designate the database as authoritative only after a verified import, and make the import idempotent. SDK metadata/backfill can later refine provenance without claiming complete pre-upgrade task history.

Session closure, host shutdown, SDK unavailability, and archival are distinct states. A closed historical session is not automatically a deleted SDK transcript. Failure to retrieve it should report unavailable/partial coverage while preserving the ledger's task archive.

8. Retrieval, daily summaries, and analytics

Existing A2A task-get/list operations should return historical records through the persistent store. Date-aware session lookup and recall can be host-internal APIs/tools initially; do not extend A2A with invented session semantics. A read-only history tool should accept bounded agent-scoped date ranges, state/activity filters, and optional text terms. Return stable record references and paging, not arbitrary SQL access.

  1. Resolve natural-language time to an explicit interval and calendar/workday policy.
  2. Search that agent's daily summaries, then matching task messages, artifacts, and session message projections.
  3. Fetch supporting records for each candidate; show source task/session/day references, including partial coverage.
  4. For analytics, query authoritative timestamps/state. Summaries may explain the count, never determine it.

For an agent-specific completed-task count, count distinct owner/task pairs completed during the interval. Activity queries include messages/transitions during the interval even for tasks created earlier. For multi-agent reports, provide separate counts for all executions and primary user outcomes; delegated tasks and completed routing tasks are not automatically additional delivered outcomes. Related-task links alone are insufficient to infer acceptance.

8.1 Daily working-context to memory cycle

  1. During the day: retain the physical conversation across turns, preserving normal same-day context. Persist sanitized task and conversation evidence incrementally.
  2. After the day boundary: review the day's recorded activity across all contributing sessions and synthesize decisions, commitments, unresolved questions, and useful discoveries. Distinguish user statements, observed results, and model inferences; preserve uncertainty and source references.
  3. At the next day's first new turn: start a fresh physical conversation and supply a bounded selection of relevant synthesized memories. Expose read-only history tools so the model can verify details or retrieve other dates when needed.
  4. As evidence changes: revise or supersede memories when later work resolves a question or contradicts an earlier interpretation. Retain provenance and avoid treating repeated summaries as independent evidence.

Make daily summaries versioned and traceable to their inputs and generation policy; do not require identical model prose on regeneration. Generate after the cutoff, either by a scheduled job or lazily at the next activity, with a source watermark and incomplete marker for spanning tasks. Do not interrupt an active turn to synthesize it or await a pending input/authentication callback. Regenerate or invalidate when late records arrive. Activity after the boundary is searchable under its real date even when the physical conversation started the previous day.

If the host was stopped overnight, perform a bounded catch-up synthesis attempt before admitting the next day's first new turn. Run synthesis outside the active task's conversation, without side-effecting tools or authority to execute commitments. Exact scheduling, inference budgets, and controls remain open. Derivation failures must not block durable task writes or indefinitely block new work: mark memory coverage incomplete, admit the task with an explicit coverage limitation, and retain source-based recall as a fallback. Durable task state and deterministic analytics remain authoritative.

Summarization may incur inference cost and expose source content to the configured inference service. Keep it bounded, policy-controlled, and separate from arbitrary tool execution. Do not run a summarizer inside the active task's SDK turn, pollute that conversation, or silently grant it permission to carry out unfinished tasks. Synthesized memories are revisable historical context, not trusted instructions or proof that a commitment was completed. Cross-day consolidation into longer-term memory remains a separate, provenance-aware feature.

Start with metadata and text queries. Embeddings, cross-agent memory synthesis, and proactive recall beyond the bounded next-day grounding policy are later choices. Daily memory grounding belongs to the combined daily compaction stage, not the initial task archive. An agent's topic boundary is a useful retrieval scope, not a security boundary.

9. Privacy, retention, and portability

Persistent task history newly makes user requests, results, and artifacts durable. Store it in private host state, not the source repository. Do not present local SQLite as encryption or per-caller access control; all current trusted local callers of an agent share its history. Hosted multi-user storage needs a separate authenticated identity/authorization design.

Persist sanitized public messages and explicitly allowlisted session text. Strip temporary authorization URLs from both text and structured AuthRequired messages, discard codes/tokens/client secrets/raw auth events, and retain only a generic sign-in-needed marker and nonsecret server identity. Apply the same filter to task snapshots, transitions, history projections, exports, and summaries. Arbitrary user-pasted secrets cannot be eliminated reliably by a general redactor; documentation and deletion tools remain necessary.

No silent automatic expiry is proposed initially. Provide explicit agent/task/date-range deletion and export with clear scope and confirmation, including derived summaries and any search indexes. Mark summaries stale or regenerate them after source deletion. Document that deleting RepoYak history does not automatically delete SDK transcripts, backups, workspace artifacts, or effects in external services; coordinated deletion should be a separate explicit choice.

Exports should carry versioned schema, agent identity, UTC/time policy, tasks, session associations, sanitized messages, coverage, and source relationships. A future per-agent folder archive can meet the note's portability goal without coupling live storage to catalog layout. Backup/restore must preserve the host/history identity and prevent a copied archive from accidentally joining another active execution ledger.

11. Decisions for review

  1. Storage placement: accept a host-wide private SQLite ledger with agent-scoped export, or prefer live per-agent ledgers for portability?
  2. Resolved — meaning of session: a physical SDK conversation, with flexible daily boundaries. Rotate between tasks, not forcibly at midnight; do not create logical slice identities as sessions.
  3. Resolved — daily context lifecycle: daily sessions are the user's working-context boundary, paired with end-of-day synthesis and next-day recall of source-linked, revisable memories. Design and ship rotation with memory continuity rather than as an isolated reset; persistence can still ship first.
  4. Day policy: midnight calendar day as default, or an explicit workday cutoff such as 4 a.m.? Decide default query semantics and travel/timezone-change behavior.
  5. History coverage: is a durable public task archive plus user/assistant projection sufficient, or is a broader raw runtime archive required? A broader archive needs a separate privacy/retention design.
  6. Memory policy details: choose scheduled versus lazy synthesis, bounded catch-up/retry behavior, operator controls, relevance selection, context budgets, and correction/supersession behavior. Bounded next-day memory grounding and read-only model recall are the design direction; raw transcript carry-forward and automatic execution of commitments are not. Costs and confidentiality apply independently of persistence.
  7. Retention and identity migration: keep until explicit deletion, and require explicit history-scope migration for workspace moves? Define whether archival hides discovery without stopping execution.

The imported note's questions about saga failure/retry/compensation, conference ownership, router bottlenecks, effortless agent creation, and cross-agent memory remain valid. Preserve room for them without making durable task storage depend on solving orchestration.
